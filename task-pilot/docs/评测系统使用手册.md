## 1. 系统概述

task-pilot 是一个基于 Kubernetes 的自动化评测任务调度系统。它把「用例集定义」与「执行编排」分离，对每条用例执行**二段式流程**：

```text
         ┌─────────────── 一条用例的执行（CaseExecution）───────────────┐
用例  →  测试任务 TestTask（被测模型执行）  →  评测任务 EvalTask（评测 LLM 判定）  →  PASSED / FAILED
         claude -p '<任务描述>'               逐条判定校验点，产出 verdict.json
```

**关键特性：**

- **评测隔离**：测试任务只拿到「任务描述 + 输入文件 + 被测模型端点」，**拿不到校验点**；校验点仅在评测阶段提供给评测 LLM，保证被测方无法预知评测标准。
- **LLM 评测**：校验点是**纯文本描述**，由评测 LLM 逐条判定是否通过，而非硬编码规则。
- **评测 Prompt 完全自定义**：指导评测 LLM 的 prompt 由用户通过接口上传/查看/修改/删除；创建执行任务时选定一个 prompt，其内容会被快照到本次执行，保证历史结果可复现。
- **全局并发控制**：所有执行任务的用例共享一个全局并发上限（`max_concurrent_tasks`），排队调度，避免瞬间灌爆集群。
- **配置中心**：被测模型端点（`base_url`/`model_name`/`api_key`）多套可配，api_key 加密存储、脱敏返回。

## 2. 核心概念与数据模型

### 2.1 实体关系

```text
TargetEndpoint（被测模型端点，多套）
        │ 被 EvalRun 选用
EvalPrompt（评测 prompt，用户自定义，多套）
        │ 被 EvalRun 选用（内容快照到 run）
CaseSet（用例集）
   └── Case（用例：任务描述 + 关联文件 + 校验点）
          └── Checkpoint（纯文本校验点）
        │ 一次执行
EvalRun（执行任务，冻结用例集快照 + prompt 快照）
   └── CaseExecution（单条用例执行，桥接 TestTask + EvalTask）
          └── CheckResult（评测 LLM 对每个校验点的判定）
FileObject（上传的文件：输入 input / 产物 artifact）
```

### 2.2 实体职责速查

| 实体 | 作用 | 关键字段 |
|------|------|----------|
| `TargetEndpoint` | 被测模型端点配置 | `id`, `name`, `base_url`, `model_name`, `api_key`(加密), `is_default` |
| `EvalPrompt` | 用户自定义评测 prompt | `id`, `name`, `content`, `is_default` |
| `FileObject` | 上传文件 | `file_id`, `filename`, `size`, `purpose`, `sha256` |
| `CaseSet` | 用例集 | `id`, `name`, `version`, `cases[]` |
| `Case` | 单条用例 | `id`, `name`, `description`, `file_ids[]`, `checkpoints[]` |
| `Checkpoint` | 文本校验点 | `id`, `order_no`, `description` |
| `EvalRun` | 执行任务 | `id`, `status`, `total/passed/failed/errored`, `case_executions[]` |
| `CaseExecution` | 用例执行 | `id`, `status`, `test_task_id`, `eval_task_id`, `check_results[]` |
| `CheckResult` | 校验点判定 | `order_no`, `passed`, `reason` |

## 3. 完整使用流程

一次完整评测流程如下（`②③④'` 可预先准备好、复用）：

```text
① 上传输入文件      POST /api/v1/files/upload            → 得到 file_id
② 配置被测端点      POST /api/v1/config/target-endpoints → 得到 endpoint_id（设为默认）
③ 配置评测 prompt   POST /api/v1/eval-prompts            → 得到 prompt_id（设为默认，可选，已内置 default）
④ 创建用例集        POST /api/v1/case-sets               → 得到 case_set_id（校验点为纯文本）
⑤ 创建执行任务      POST /api/v1/eval-runs               → 得到 eval_run_id（排队等待调度）
⑥ 轮询进度          GET  /api/v1/eval-runs/{id}          → 直到 status 终态
⑦ 查询结果          GET  /api/v1/eval-runs/{id}/results  → 逐条校验点 passed/reason
```

## 4. API 调用指南

- **Base 路径**：`/api/v1`（健康检查除外：`/healthz`）
- **服务地址**：下文示例统一用 `${BASE_URL}` 表示评测服务的访问地址，使用前先设置，例如：`export BASE_URL=http://<host>:<port>`
- **Content-Type**：JSON 接口用 `application/json`；文件上传用 `multipart/form-data`
- **错误响应**：统一为 `{"error": "错误信息"}`

### 4.0 健康检查

```bash
curl -s ${BASE_URL}/healthz
```
响应 `200`：
```json
{"name":"task-pilot","status":"ok"}
```

### 4.1 文件管理

#### 上传文件 `POST /api/v1/files/upload`

`multipart/form-data` 表单字段：

| 字段 | 必填 | 说明 |
|------|------|------|
| `file` | 是 | 文件内容 |
| `purpose` | 否 | `input`(默认) 或 `artifact` |
| `task_id` | 否 | 关联任务 ID |

```bash
curl -s -X POST ${BASE_URL}/api/v1/files/upload \
  -F "file=@./sales_h1_2025.csv" \
  -F "purpose=input"
```
响应 `201`：
```json
{
  "file_id": "file-1c388e57e5967924",
  "filename": "sales_h1_2025.csv",
  "size": 812,
  "purpose": "input",
  "sha256": "47ba2a2a..."
}
```
> 大小上限由 `max_file_size_mb`（默认 10MB）控制，超限返回 `400`。

#### 下载文件 `GET /api/v1/files/{file_id}/download`

```bash
curl -OJ ${BASE_URL}/api/v1/files/file-xxxx/download
```
> 带 `?task_id=` 时需请求头 `X-Task-Token`（executor 内部回调用），普通下载可省略。

### 4.2 配置中心：被测模型端点

#### 新增端点 `POST /api/v1/config/target-endpoints`

请求体：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | 端点别名（唯一） |
| `base_url` | 是 | 被测模型 API 基址 |
| `model_name` | 是 | 模型名 |
| `api_key` | 否 | 密钥（加密存储；更新时留空表示保留原值） |
| `is_default` | 否 | 是否默认端点（EvalRun 未指定端点时使用） |

```bash
curl -s -X POST ${BASE_URL}/api/v1/config/target-endpoints \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "analysis-endpoint",
    "base_url": "https://your-model-endpoint/v1",
    "model_name": "deepseek-v4-flash",
    "api_key": "sk-xxxx",
    "is_default": true
  }'
```
响应 `201`（api_key **脱敏**）：
```json
{
  "id": "ep-5138963efec75136",
  "name": "analysis-endpoint",
  "base_url": "https://your-model-endpoint/v1",
  "model_name": "deepseek-v4-flash",
  "api_key_masked": "****xxxx",
  "is_default": true
}
```

#### 其他端点接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/config/target-endpoints` | 列出全部（api_key 脱敏） |
| GET | `/api/v1/config/target-endpoints/{id}` | 单个详情 |
| PUT | `/api/v1/config/target-endpoints/{id}` | 更新（字段同新增，api_key 留空保留） |
| DELETE | `/api/v1/config/target-endpoints/{id}` | 删除 |

> `is_default=true` 时会自动清除其他端点的默认标记，保证全局唯一默认。

### 4.3 用例集

#### 创建用例集 `POST /api/v1/case-sets`

请求体结构见 [5.1 用例集数据格式](#51-用例集提交格式)。

```bash
curl -s -X POST ${BASE_URL}/api/v1/case-sets \
  -H 'Content-Type: application/json' \
  -d @case-set.json
```
响应 `201`：返回完整 `case_set`（含生成的 `id`、`version`、各 `case` 与 `checkpoint` 的 id）。

#### 其他用例集接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/case-sets` | 列表（不含用例明细） |
| GET | `/api/v1/case-sets/{id}` | 详情（含用例与校验点，按 order_no 排序） |
| PUT | `/api/v1/case-sets/{id}` | 覆盖式更新（version 自增，替换全部用例） |
| DELETE | `/api/v1/case-sets/{id}` | 删除（级联删除用例与校验点） |

### 4.4 执行任务（EvalRun）

#### 创建执行任务 `POST /api/v1/eval-runs`

请求体：

| 字段 | 必填 | 说明 |
|------|------|------|
| `case_set_id` | 是 | 要执行的用例集 ID |
| `name` | 否 | 执行任务名（缺省自动生成） |
| `endpoint_id` | 否 | 被测端点 ID（缺省用默认端点） |
| `prompt_id` | 否 | 评测 prompt ID（缺省用默认 prompt；内容会被快照到本次执行） |

```bash
curl -s -X POST ${BASE_URL}/api/v1/eval-runs \
  -H 'Content-Type: application/json' \
  -d '{"case_set_id":"cs-927b30d65133b050","name":"数据分析-E2E"}'
```
响应 `201`：
```json
{
  "eval_run": {
    "id": "er-bec348c1602d9549",
    "name": "数据分析-E2E",
    "case_set_id": "cs-927b30d65133b050",
    "endpoint_id": "ep-5138963efec75136",
    "status": "RUNNING",
    "total": 1, "passed": 0, "failed": 0, "errored": 0,
    "case_executions": [
      {"id":"ce-xxx","case_name":"H1销售数据分析","status":"PENDING","order_no":0}
    ]
  }
}
```
> 创建后用例进入 `PENDING` 队列，由调度器按全局并发额度派发，**不会立即启动全部 Job**。

#### 其他执行任务接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/eval-runs` | 列表（不含用例明细，最多 100 条） |
| GET | `/api/v1/eval-runs/{id}` | 进度详情（含各用例状态与 task_id） |
| GET | `/api/v1/eval-runs/{id}/results` | **完整结果**（含逐条校验点判定） |
| POST | `/api/v1/eval-runs/{id}/stop` | 停止（删除未完成用例的 Job，置 STOPPED） |
| DELETE | `/api/v1/eval-runs/{id}` | 删除（先停止再软删，级联删除用例与校验结果） |

### 4.5 评测 Prompt 管理（用户自定义）

指导评测 LLM 判定校验点的 prompt 完全由用户自定义。创建执行任务时可用 `prompt_id` 选定；系统首次启动会自动种入一条名为 `default` 的默认 prompt。

#### prompt 内容编写要求

评测 prompt 必须引导评测模型输出**规定 schema 的纯 JSON**，否则结果无法解析（用例会判 ERROR）。约定：

- 输出 `{"overall":"pass|fail","checkpoints":[{"index":0,"passed":true,"reason":"..."}]}`；
- `checkpoints[].index` 与校验点数组下标一一对应（从 0 开始）；
- 服务以逐条 `passed` 聚合判定，全部通过才 PASSED。

评测阶段实际喂给评测 LLM 的内容 = **你的 prompt 内容** + 自动附加的「评测输入(JSON：任务描述/校验点/测试日志)」+「被测系统产物内容」。因此 prompt 里可直接引用这些信息。

#### 新增 prompt `POST /api/v1/eval-prompts`

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | prompt 名称（唯一） |
| `content` | 是 | prompt 正文 |
| `is_default` | 否 | 设为默认（EvalRun 未指定 prompt 时使用） |

```bash
curl -s -X POST ${BASE_URL}/api/v1/eval-prompts \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "严格评测v1",
    "content": "你是严格的评测专家。请根据「评测输入」中的任务描述与校验点，以及「被测系统产物内容」，逐条判定每个校验点是否通过。只输出 JSON，不要 markdown：{\"overall\":\"pass|fail\",\"checkpoints\":[{\"index\":0,\"passed\":true,\"reason\":\"依据\"}]}。checkpoints[].index 与校验点下标一一对应，全部通过 overall 才为 pass。",
    "is_default": true
  }'
```
响应 `201`：
```json
{
  "id": "prompt-xxxxxxxx",
  "name": "严格评测v1",
  "content": "你是严格的评测专家。……",
  "is_default": true
}
```

#### 其他 prompt 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/eval-prompts` | 列出全部 prompt |
| GET | `/api/v1/eval-prompts/{id}` | 查看单个 prompt（含完整 content） |
| PUT | `/api/v1/eval-prompts/{id}` | 修改（字段同新增，`content` 留空表示保留原值） |
| DELETE | `/api/v1/eval-prompts/{id}` | 删除 prompt |

```bash
# 查看
curl -s ${BASE_URL}/api/v1/eval-prompts/prompt-xxxx
# 修改（仅改名，不动内容）
curl -s -X PUT ${BASE_URL}/api/v1/eval-prompts/prompt-xxxx \
  -H 'Content-Type: application/json' \
  -d '{"name":"严格评测v2","is_default":true}'
# 删除
curl -s -X DELETE ${BASE_URL}/api/v1/eval-prompts/prompt-xxxx
```

> `is_default=true` 时会自动清除其他 prompt 的默认标记，保证全局唯一默认。
> **prompt 内容在 EvalRun 创建时被快照**，之后即使修改/删除该 prompt，也不影响已创建执行任务的结果。

## 5. 数据格式规范

### 5.1 用例集提交格式

`POST /api/v1/case-sets` 请求体：

```json
{
  "name": "用例集名称",
  "description": "用例集描述（可选）",
  "cases": [
    {
      "name": "用例名称",
      "description": "任务描述——交给被测模型执行的指令",
      "file_ids": ["file-xxxx"],
      "checkpoints": [
        "校验点1（纯文本，仅评测LLM可见）",
        "校验点2"
      ]
    }
  ]
}
```

字段约束：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `name` | string | 是 | 用例集名 |
| `description` | string | 否 | 用例集描述 |
| `cases` | array | 是 | 至少 1 条用例 |
| `cases[].name` | string | 是 | 用例名 |
| `cases[].description` | string | 是 | **任务描述**，下发给被测模型（不含校验点） |
| `cases[].file_ids` | string[] | 否 | 关联文件 ID，须先经 `/files/upload` 上传获得 |
| `cases[].checkpoints` | string[] | 是 | **纯文本校验点数组**，仅评测阶段可见 |

**编写要点：**
- 任务描述应明确告知被测模型：输入文件在哪（`input/` 目录）、要做什么、结果写到哪（约定写入 `output/`）。
- 校验点应是**可客观判定**的陈述句，让评测 LLM 能据测试产出判断真伪。避免主观模糊表述。

### 5.2 关联文件在容器内的位置

- 上传的 `file_ids` 会在测试任务容器内被下载到 `$WORKSPACE/input/`（`$WORKSPACE=/workspace/tasks/<task-id>`，每任务独立 emptyDir，硬隔离）。
- 被测模型命令在 `$WORKSPACE` 下执行，用相对路径读 `input/`、写 `output/`。
- 命令结束后 `output/` 会被打包为 `output.tar.gz` 上传为 artifact。

### 5.3 verdict.json 格式（评测产出，系统内部）

评测任务由评测 LLM 产出，服务据此判定。格式：

```json
{
  "overall": "pass|fail",
  "checkpoints": [
    {"index": 0, "passed": true,  "reason": "判定依据"},
    {"index": 1, "passed": false, "reason": "未通过原因"}
  ]
}
```
- `checkpoints[].index` 与用例校验点数组下标一一对应（从 0 开始）。
- 服务以**逐条 `passed` 聚合**判定用例，`overall` 仅参考。

### 5.4 结果响应格式（`/results`）

```json
{
  "eval_run": {
    "id": "er-xxx",
    "status": "SUCCEEDED",
    "total": 1, "passed": 1, "failed": 0, "errored": 0,
    "case_executions": [
      {
        "id": "ce-xxx",
        "case_name": "H1销售数据分析",
        "status": "PASSED",
        "test_task_id": "task-aaa",
        "eval_task_id": "task-bbb",
        "message": "all checkpoints passed",
        "check_results": [
          {"order_no": 0, "passed": true, "reason": "结论指出 WidgetA 销量持续上升"}
        ]
      }
    ]
  }
}
```

## 6. 状态流转与判定规则

### 6.1 用例执行状态（CaseExecution.status）

```text
PENDING ──(调度器派发测试任务)──> TEST_RUNNING ──(测试成功)──> TEST_DONE
                                       │                          │(调度器派发评测任务)
                                       │(测试失败)                 ▼
                                       └──> ERROR            EVAL_RUNNING ──(评测成功)──┬─> PASSED（全部校验点通过）
                                                                  │                     └─> FAILED（任一未通过）
                                                                  └(评测失败/无verdict)─> ERROR
（任意阶段被停止）──────────────────────────────────────────────────────────────────> STOPPED
```

| 状态 | 含义 |
|------|------|
| `PENDING` | 已入队，等待调度派发测试任务 |
| `TEST_RUNNING` | 被测模型执行中 |
| `TEST_DONE` | 测试完成，等待调度派发评测任务 |
| `EVAL_RUNNING` | 评测 LLM 判定中 |
| `PASSED` | 全部校验点通过 |
| `FAILED` | 存在未通过的校验点 |
| `ERROR` | 测试或评测**执行本身**异常（非业务判定失败） |
| `STOPPED` | 被主动停止 |

> **PASSED/FAILED 与 ERROR 的区别**：PASSED/FAILED 是评测 LLM 的业务判定结果；ERROR 表示流程没跑通（如镜像缺失、评测未产出 verdict）。

### 6.2 执行任务状态（EvalRun.status）

| 状态 | 含义 | 触发条件 |
|------|------|----------|
| `RUNNING` | 有用例未达终态 | 创建后默认 |
| `SUCCEEDED` | 全部用例 PASSED | 所有用例终态且无 FAILED/ERROR |
| `FAILED` | 存在 FAILED 或 ERROR | 所有用例终态但有失败 |
| `STOPPED` | 被主动停止 | 调用 /stop |

聚合计数：`total`（总数）/ `passed` / `failed` / `errored`。

### 6.3 判定规则

- **单条用例**：当且仅当其**所有**校验点 `passed=true` 时判 `PASSED`；任一 `false` 判 `FAILED`。
- **执行任务**：所有用例达终态后，无 FAILED/ERROR 则 `SUCCEEDED`，否则 `FAILED`。

### 6.4 并发调度

- 全局并发上限由服务端配置 `scheduler.max_concurrent_tasks`（默认 20）控制。
- 额度统一计入**测试任务 + 评测任务**的运行中数量，跨所有 EvalRun 共享。
- 调度器每轮按空闲额度 FIFO 出队：**优先派发待评测用例**（尽快释放额度），再派发待测试用例。
- `max_concurrent_tasks<=0` 表示不限流。

### 8.1 数据文件（sales_h1_2025.csv 节选）

数据内嵌可验证结论：WidgetA 销量逐月上升、East 区 WidgetB 逐月下滑。

### 8.2 分步执行

```bash
  -F "file=@./sales_h1_2025.csv" -F "purpose=input" | jq -r '.file_id')

  | jq -r '.id')

      \"file_ids\": [\"$FILE_ID\"],
      \"checkpoints\": [
        \"结论应指出 WidgetA 的销量在 1 月到 6 月整体呈持续上升趋势\",

# ④ 创建执行任务

  sleep 5
done

# ⑥ 查看结果
curl -s $BASE/api/v1/eval-runs/$ER_ID/results | jq '.eval_run'
```

## 9. 错误码与常见问题

### 9.1 HTTP 状态码

| 码 | 含义 |
|----|------|
| `200` | 查询/更新成功 |
| `201` | 创建成功 |
| `400` | 请求参数错误（缺必填字段、文件超限、purpose 非法等） |
| `401` | 缺少/无效 `X-Task-Token`（仅内部回调接口） |
| `404` | 资源不存在 |
| `500` | 服务端错误 |

### 9.2 常见问题

| 现象 | 原因 | 处理 |
|------|------|------|
| 创建 EvalRun 报 `no default target endpoint configured` | 未配置默认端点且未指定 endpoint_id | 先建 `is_default:true` 端点，或请求带 `endpoint_id` |
| 用例长期停在 `PENDING` | 全局并发额度被占满 | 等待在跑用例完成释放额度，或调大 `max_concurrent_tasks` |
| 用例 `ERROR`，message 含 `UNIQUE constraint failed: tasks.request_id` | 旧版 bug（已修复） | 升级到最新版本并重置数据库 |
| 用例 `ERROR`，message 含 `command not found` / 镜像相关 | 执行镜像缺 `lumi-model-setup`/`claude`，或评测镜像缺失 | 更换为含对应 CLI 的镜像 |
| 用例 `ERROR`，message 含 `parse verdict`/`verdict.json not found` | 评测 LLM 未按格式输出 JSON | 检查评测端点可用性，必要时调整评测 prompt |
| `/results` 用 jq 报 `Cannot iterate over null` | 用例为 ERROR 时 `check_results` 为 null | jq 表达式加 `// []` 兜底 |
| 测试任务成功但评测才启动 | **正常设计**（二段式串行） | 评测必须拿到测试产出才能判定，无法并行 |

### 9.3 资源清理

```bash
curl -s -X DELETE ${BASE_URL}/api/v1/eval-runs/er-xxx
curl -s -X DELETE ${BASE_URL}/api/v1/case-sets/cs-xxx
curl -s -X DELETE ${BASE_URL}/api/v1/config/target-endpoints/ep-xxx
```
